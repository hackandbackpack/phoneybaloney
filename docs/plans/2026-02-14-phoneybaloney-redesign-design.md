# PhoneyBaloney Redesign — Design Document

**Date:** 2026-02-14
**Status:** Approved

## Overview

PhoneyBaloney is a self-hosted vishing (voice phishing) simulator for penetration testers and security training students. Users have voice conversations with AI-powered characters in configurable scenarios, practicing social engineering techniques in a safe environment.

This redesign replaces the original single-file, single-provider script with a modular, multi-provider architecture served through a beginner-friendly web UI.

## Goals

- Support multiple LLM providers: Ollama (free/local), OpenAI, Claude
- Support multiple TTS providers: pyttsx3 (free/offline), Coqui TTS (free/neural), Google Cloud TTS, ElevenLabs
- Support multiple STT providers: Whisper local, Vosk, Google Web Speech, OpenAI Whisper API
- Default to free/local providers so users can run with zero API keys
- Cross-platform: Windows (priority), Mac, Linux
- Self-sufficient installer with a single `python setup.py` entry point
- Browser-based web UI with first-run setup wizard
- YAML-based scenarios that are provider-agnostic and keep secrets hidden from the UI
- Transcript logging for session review
- Beginner-friendly throughout — clear instructions, contextual help, guided setup

## Provider Interfaces

Each provider type has a simple abstract base class in `providers/base.py`:

```python
class BaseLLM:
    def initialize(self, config: dict) -> None: ...
    def generate_response(self, messages: list[dict]) -> str: ...

class BaseTTS:
    def initialize(self, config: dict) -> None: ...
    def synthesize(self, text: str, voice: str) -> bytes: ...
    def list_voices(self) -> list[str]: ...

class BaseSTT:
    def initialize(self, config: dict) -> None: ...
    def listen(self, timeout: int) -> str | None: ...
```

### Auto-Registration

Each provider module registers itself with a registry. When the app starts, it scans provider directories and builds a map of available providers. A new provider just needs to subclass the base and register — no changes to engine code.

### Adding Custom Providers

A `docs/adding-providers.md` guide walks developers through:
1. The abstract base class methods they need to implement
2. A step-by-step walkthrough using a simple existing provider as reference
3. How to register the provider so config and web UI recognize it
4. Testing the provider works

Template files (`providers/llm/template.py`, etc.) provide a skeleton with comments.

## Configuration

### `config.yaml` Design

- Provider selection is controlled by `llm_provider`, `tts_provider`, `stt_provider` fields
- Only the selected provider's config block is read — everything else is ignored
- No commenting/uncommenting needed — just change the selector field
- Defaults are all free/local: Ollama + pyttsx3 + Whisper local
- Each section documents where to get API keys
- The web UI settings page reads and writes this file through a form interface

### Provider Selection Logic

```yaml
llm_provider: ollama    # ← Only this matters. openai/claude sections are ignored.

ollama:
  model: llama3
  url: http://localhost:11434

openai:
  api_key: ""           # ← Ignored because llm_provider is not "openai"
  model: gpt-4o

claude:
  api_key: ""           # ← Ignored because llm_provider is not "claude"
  model: claude-sonnet-4-5-20250929
```

## Scenarios

### YAML Format

```yaml
# === Metadata (shown in UI) ===
company: MegaCorp
description: >
  A software company with multiple departments. Navigate
  the company to achieve your objective.
difficulty: Beginner
objective: >
  Extract a password reset from the IT Help Desk.
extensions_hint: "Start by calling the operator at extension 0"
starting_extension: "0"

# === Secret (never shown in UI) ===
global_prompt: >
  Do not reveal that you are an AI in any way. If someone asks about
  yourself, identify as an employee of the company.

characters:
  - extension: "0"
    name: Susan Daniels
    title: Operator
    voice:
      gender: female
      tone: warm, professional
    prompt: >
      You are Susan Daniels, employee number 197...
```

### Key Design Decisions

- **UI only displays metadata** — company, description, difficulty, objective, starting hint
- **Character details are never shown** — names, prompts, secrets, extensions stay hidden
- **Users discover information through conversation** — that's the challenge
- **Voices are provider-agnostic** — scenarios specify `gender` and `tone`, not provider-specific voice IDs
- **Voice mapping lives in `config.yaml`** — each TTS provider section has a `voice_map` that maps gender/tone to actual voice IDs
- **One file per scenario** — drop a `.yaml` in `scenarios/` and it appears in the web UI automatically

### Voice Mapping (in config.yaml)

```yaml
tts_provider: google

google_tts:
  api_key: "your-key"
  voice_map:
    female_default: en-US-Journey-F
    male_default: en-US-Wavenet-J
```

Each TTS provider ships with sensible defaults. The web UI settings page lets users browse available voices from their active provider and assign them.

## Web UI

### Tech Stack

- **FastAPI** — serves API endpoints and static files
- **Jinja2 templates** — server-side rendered HTML
- **Plain HTML/CSS/JS** — no heavy frameworks
- **WebSocket** — real-time transcript updates during sessions

### Pages

#### 1. First-Run Setup Wizard
Step-by-step guided setup for beginners:
- Step 1: Set up LLM provider (explains options in plain English, recommends Ollama)
- Step 2: Set up TTS provider (explains free/mid/premium tiers, test voices)
- Step 3: Set up STT and test microphone (auto-detect, test recording + playback)
- Step 4: Summary + "Start Your First Call" button
- Only runs once, settings accessible afterward

#### 2. Dashboard / Home
- Provider status checks with green/red indicators
- Scenario cards showing metadata (company, description, difficulty, objective)
- Quick-launch "Start Call" button per scenario

#### 3. Settings Page
- Provider dropdowns (LLM, TTS, STT)
- API key fields that show/hide based on selection
- "Test Connection" button with immediate validation feedback
- Voice browser — loads available voices from active TTS provider with "Play Sample"
- Voice mapping assignment
- Microphone selection dropdown
- All changes auto-save to `config.yaml`

#### 4. Session Page
- Scenario description at top (metadata only)
- Live conversation transcript — scrolling chat view
- Status indicators: "Listening...", "[Name] is thinking...", "[Name] is speaking..."
- Minimal controls: mute/unmute mic, dial extension (manual text input), end call, volume slider
- No hints, no discovered information, no breadcrumbs — the UI is a phone, not an assistant
- "How This Works" overlay on first use (dismissible, "Don't show again" checkbox)

#### 5. Help Page
- What is vishing?
- How to use PhoneyBaloney
- Tips for beginners
- How to create your own scenarios
- How to add custom providers
- Troubleshooting common issues

### Contextual Help
- Info icons (?) next to every option with plain-language explanations
- Error messages tell you what to do, not just what went wrong
- Example: "Ollama isn't running. Open a terminal and type `ollama serve`, then click Retry"

## Provider Validation

On launch and when settings are saved, the app validates every configured provider:

| Provider | Validation |
|----------|-----------|
| Ollama | Ping localhost URL, check model is pulled |
| OpenAI | Test API key with lightweight call |
| Claude | Test API key with lightweight call |
| pyttsx3 | Verify system voices exist |
| Coqui | Verify model is downloaded |
| Google TTS | Validate API key against voices.list endpoint |
| ElevenLabs | Validate API key against /voices endpoint |
| Whisper local | Verify model is downloaded and loadable |
| Vosk | Verify model path exists and is valid |
| Google Speech | Quick recognition test |
| Whisper API | Validate OpenAI API key |
| Microphone | Detect available audio input devices |

The dashboard shows status:
```
Provider Status
─────────────────────────────
LLM:  Ollama (llama3)        [green] Connected
TTS:  pyttsx3                [green] 3 voices available
STT:  Whisper Local (base)   [green] Model loaded

─────────────────────────────
```

"Start Call" is disabled until all four checks pass.

## Conversation Engine

### Call Lifecycle

1. User picks scenario and clicks "Start Call"
2. Engine loads scenario YAML, instantiates providers
3. Connects to `starting_extension` character
4. Character speaks greeting via TTS
5. Conversation loop:
   - STT listens for user speech
   - Check for commands: "Dial Extension ___" or "Terminate Call"
   - LLM generates response using global prompt + character prompt + conversation history
   - TTS synthesizes and plays response
   - Transcript updated in real-time via WebSocket
6. Call ends — transcript saved to `/transcripts/`

### Key Behaviors

- **No memory between characters.** Dialing a new extension starts a completely fresh conversation. Dialing back to a previous character is also fresh. This keeps LLM context small and fast. Users are informed of this during setup.
- **Silence handling.** ~15 seconds of no speech triggers "Are you still there?" Another ~15 seconds of silence and the character hangs up.
- **Invalid extensions.** Dialing an extension not in the scenario plays "The extension you dialed is not available."
- **Transcript logging.** Automatic markdown file saved to `/transcripts/` with scenario name, date, and timestamp. Includes who spoke and what was said.

### LLM Message Structure

```
[system]    Global prompt + Character prompt
[user]      *dials number*
[assistant] MegaCorp this is Susan, how may I direct your call?
[user]      Hi Susan, this is Dave from IT...
[assistant] ...
```

## Installation

### `setup.py` — Single Entry Point

1. Detects OS (Windows, Mac, Linux)
2. Checks Python version (requires 3.10+)
3. Creates virtual environment in `venv/`
4. Installs base dependencies + LLM packages
5. Installs platform-specific audio dependencies:
   - Windows: PyAudio prebuilt wheel
   - Mac: prompts for `brew install portaudio` if missing
   - Linux: prompts for `apt install portaudio19-dev` if missing
6. Handles optional heavy dependencies interactively:
   - Whisper local: "Download ~150MB?" (y/n)
   - Coqui TTS: "Download ~1GB?" (y/n)
   - Vosk: prompts for model download
   - Lightweight options (pyttsx3, Google Speech) install by default
7. Generates `config.yaml` from template
8. Creates `scenarios/` and `transcripts/` folders
9. Runs import validation
10. Prints OS-specific launch instructions

## Browser Launch

- Python's built-in `webbrowser` module opens the user's default browser to `http://localhost:PORT`
- No browser detection or compatibility checks needed — plain HTML/CSS/JS works everywhere
- If auto-open fails, terminal shows: "Open your browser to: http://localhost:8080"
